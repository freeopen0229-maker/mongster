# 퓨전 다마고치 RPG 경제·펫 시스템 통합 명세 V2

2026-10-23. 이번 사용자 명세를 기준으로 중복과 충돌을 정리한 문서다.
기존 V1 문서와 다른 경제/등급/히든 수는 이 문서를 우선한다.

## 적용 상태

**완료:** UnityEngine에 의존하지 않는 공용 C# 모델, 서버 도메인 서비스, 로컬 원자적 저장소,
중복 요청/잔액/소유권/한정 수량 검사, Mono 컴파일 및 실행 검사.

**미완료:** 실제 DB·인증·HTTP, Apple/Google 결제 검증 어댑터, 레이드 완료 검증 어댑터,
서버 간 메시지 방송, Unity 경제 UI/도감 시리얼 툴팁, 신규 5등급 비주얼 연결,
V1 저장 데이터의 실제 이관, 실기기·결제·다중 서버·렌더링 테스트.
프로젝트가 실제 유료 서비스를 제공하는 상태를 뜻하지 않는다.

## 중복 및 충돌 정리

| 항목 | 통합 결정 |
|---|---|
| UserCurrency 중복 코드 | EconomyData.cs에 구조체 하나만 정의 |
| PetData/등급/슬롯 | namespace FusionTamagotchi의 V2 모델 하나로 정의 |
| 새 등급 | 일반 Common / 희귀 Rare / 영웅 Epic / 전설 Legendary / 신수 Divine |
| 기존 6등급 | V1 기존 저장/뷰포트 호환을 위해 유지. V2 등급과 숫자 캐스팅 금지 |
| 히든 | 일반 알 출신 후보 5종. A 1종 신수 / B~E 4종 전설 |
| 이전 히든 4종/1% | 폐기된 V1 기획. V2 추첨에는 사용하지 않음 |
| 과금 | 최신 명세에 따라 영롱한 알과 코스튬 가챠 허용. 스크롤 시간 단축 유지 |
| 거래 | 기존 횟수 소진/귀속/일일 제한/쿨다운 보존. V2 펫·알·재료는 별도 자산 모델 |

| 샘플 MonoBehaviour 지갑 변경 | 제거. 서버 서비스만 확정하며 클라이언트는 명령/스냅샷 사용 |
| 리롤 결과/가격 | 클라이언트 입력 금지. 서버 카탈로그 추첨/가격 계산 |

V1 PetState는 기존 6등급·육성·뷰포트용이다. V2 PetData는 새로운 스킬/히든 경제용이다.
하나의 실제 펫을 양쪽 테이블에 독립적으로 복제해 운영해서는 안 된다. 운영 적용 전
명시적 마이그레이션으로 권한 있는 원본을 하나로 정해야 한다. 현재 데모는 두 모델을
자동 동기화하지 않으며, V2 경제 서비스는 V1 PetState의 펫을 거래하지 않는다.
따라서 V1에서 획득한 펫이 새 경매 UI에 자동 나타나거나 새 등급의 외형으로 자동 바뀌지 않는다.

## 1. 재화와 상품

| 재화 | 저장 | 용도 |
|---|---|---|
| 전 | long Jeon | 케어, 리롤, 경매. 기존 Coins와 같은 잔액 |
| 보석 | int Gem | 스크롤·시즌 코스튬 가챠·영롱한 알 |
| 실타래 | int MileageThread | 가챠 중복 보상, 지난 시즌 의상 확정 구매 |

금액은 음수 불가. 연산은 checked를 사용한다. 전 지갑 한도는 기존 시스템과 같은 10^12.
소수 화폐는 사용하지 않는다. 10,000원=100보석(명목 1보석=100원)은 상품 기획 기준이며,
보석을 현금으로 환전하는 API를 의미하지 않는다.

| ShopProduct | 보석 소모 | 지급 |
|---|---:|---:|
| HatchScroll | 11 | 스크롤 1 |
| HatchScrollBundle | 100 | 스크롤 11 |
| CostumeDraw | 15 | 가챠 1회 |
| CostumeDrawTen | 135 | 가챠 10회 |
| LuminousEgg | 30 | 영롱한 알 1 |
| LuminousEggBundle | 300 | 영롱한 알 11 |

한 명령의 구매·잔액 차감·지급·영수증은 같은 transaction이다.
코스튬은 계정 소유이며 V2 경매 자산에 포함하지 않는다. 동일 10회 묶음 안에서
첫 의상을 받은 후 같은 의상이 또 나오면 중복으로 처리한다.
중복 실타래 수량/가중치/이월 의상 가격은 설정 전 사용할 수 없다.
지난 시즌 판정은 Archive.Season < CurrentSeason. 소유 의상 재구매는 거절한다.
별도 N회 확정 등급 천장은 명세에 없으므로 추가하지 않았다.

IGemPurchaseVerifier는 검증된 구매번호와 지급 보석을 반환해야 한다.
실제 어댑터는 스토어 상품 ID를 서버의 '10,000원 상품→100보석' 정책에 매핑해야 한다.
CreditVerifiedPurchase의 입력 토큰을 클라이언트가 검증 결과인 것처럼 대체하면 안 된다.
같은 구매번호는 다른 requestId·다른 계정으로 다시 지급할 수 없다.
실제 결제 검증자는 이번에 구현하지 않았고 테스트에는 Fake를 사용했다.

레이드는 IRaidRewardVerifier가 보상/완료를 검증한다. 1회 완료 ID당 한 번만 보상한다.
보석 드롭은 서버 설정 0.1~0.5% 범위에서 1개. 구체 확률은 미정이므로 기본값은 0(비활성).
아래 샘플 테스트의 0.1%는 테스트 설정일 뿐 운영 확률 확정이 아니다.
탐험/사냥/판매의 실제 완료 판정과 재화 공급량 밸런스는 별도 구현이 필요하다.

## 2. 알과 확률

일반 알: 인게임 보상. 일반/희귀 등급 확률은 아직 주어지지 않았다.
NormalCommonWeight/NormalRareWeight가 설정되지 않으면 부화를 거절하고 알을 보존한다.
일반 알에서 선택되는 종 중 HiddenType 0~4가 서버에서 지정된 종만 히든 후보가 된다.
히든 후보가 나오는 종별 비중도 종 카탈로그가 결정하므로 운영 카탈로그를 먼저 확정해야 한다.
현재 종 선택은 해당 등급의 등록 종 사이에서 균등 추첨이다. 종별 가중치가 필요하면 확장한다.

영롱한 알: 희귀 이상 보장. 히든 각성과는 다른 획득 경로다.

| 결과 | 비율 | 10,000,000구간 중 개수 |
|---|---:|---:|
| 신수 | 0.0005% | 50 |
| 전설 | 4.9995% | 499,950 |
| 영웅 | 25% | 2,500,000 |
| 희귀 | 70% | 7,000,000 |
| 일반 | 0% | 0 |

확률 합계 100%. LuminousEggOdds.Resolve는 모든 입력 구간을 정수로 분할한다.
서버 CryptoServerRandom은 암호학적 RNG와 rejection sampling으로 정수 구간을 뽑는다.
알을 구매할 때 결과 종/등급을 미리 주지 않으며 실제 부화 명령에서 추첨한다.
영롱한 알에서는 HiddenType가 지정되지 않은 종만 선택한다. 같은 등급의 적합한
종이 없으면 transaction이 실패하고 원래 알이 보존된다.
운영에서는 모든 발생 가능한 결과에 종/스킬 카탈로그가 완비돼 있어야 한다.

모든 알은 기본 8시간, 카탈로그가 8~12시간 사이로 정한다. 부화 중인 알은 거래 불가.
UseHatchScroll은 서버 UTC 부화 종료를 현재로 변경하고 스크롤 1개만 소모한다.
시간이 끝났거나 이미 부화한 알은 추가 소모하지 않는다. 실제 Hatch는 별도 명령이며,
스크롤 사용 여부는 등급 추첨/개체 스탯을 바꾸지 않는다.
알 케어에 따른 성격·개체값·잠재력은 기존 기획으로 유지하나 V2 알 케어 API는 이번에 추가하지 않았다.

## 3. 히든 각성

| 후보 | 신수/전설 변이 확률 | 코드 분모 | 한정량 |
|---|---:|---:|---|
| A (hiddenType=0) | 0.0000001% | 1,000,000,000 | 전 서버 10 |
| B~E (1~4) | 0.00005% | 2,000,000 | 종별 미정, 필수 설정 |

사용자 예제의 rand.Next(0,100000000)==0은 0.000001%로, 요구 확률보다 10배 높다.
이를 정확한 10억 분의 1로 수정했다. 영롱한 알 신수 0.0005%는 20만 분의 1이다.
세 확률은 서로 다른 이벤트다. 10억 분의 1은 매우 적은 성체 이벤트에서는
당첨이 한 번도 발생하지 않아도 이상하지 않은 수치이며 확률을 임의로 높이지 않았다.

성체 조건은 서버 PetData.level과 AdultMinLevel을 검사한다. 레벨 조건이 명세에 없어
기본값 0(미설정)에서는 각성을 실행하지 않는다. 실제 성장/경험치 서버와 연결해야 한다.
조건을 충족한 개체는 한 번만 성체 추첨한다. 같은 requestId 재시도는 기존 결과를 반환하고,
다른 requestId로 재추첨해도 isAdult/awakeningResolved 검사로 거절한다.

전 서버 잔량과 원자성을 보장하려면 운영 DB가 다음 항목을 같은 직렬화 가능한
transaction에 넣어야 한다: pet 행 잠금, quota 행 잠금, issued 증가, 시리얼 부여,
성체 확정, 스킬 확장, 영수증, AwakeningNotice outbox 추가.
로컬 InMemoryWorldStore는 단일 프로세스 lock+전체 복사로 이 계약을 흉내 내며 운영 DB가 아니다.

실패하거나 매진이면 원래 일반/희귀 고유 성체로 성장한다. 기존 희귀를 일반으로 강등하지 않는다.
B~E 한정량 미설정은 운영 오류로 처리해 성장 명령을 rollback한다.
임의의 수량을 정하거나 남은 평생 기회를 조용히 소모하지 않는다.

시리얼은 hiddenType별 발급 순서다. [No.003/010]을 그리는 도감 UI는 아직 없다.
운영 DB에는 UNIQUE(hidden_type, serial), 요청 영수증, external grant ID 제약이 필요하다.
삭제/거래/귀속으로 발급량을 되돌리지 않는다. DB 복구 시 시리얼 재사용도 금지해야 한다.
Outbox 소비자는 commit 이후 방송하며 event ID 중복 제거가 필요하다. 실제 방송 연결은 미구현.

PublicPetView에는 isHiddenPet/hiddenType이 없다. 아기 잠재 후보 플래그를 서버 응답에
그대로 넣지 않는다. 다만 특정 종만 후보라는 게임 규칙이 알려지면 종 자체로 가능성은 추측할 수 있다.
이 제한을 원치 않으면 후보 확정 시점을 종 추첨과 분리하는 추가 기획이 필요하다.

숨은 성체의 PvP 우위는 이 코드에 추가하지 않았다. 스탯 식/스킬 효과/PvP 보정 자체는
미구현이므로 'P2W 방지 밸런스까지 검증 완료'라는 의미가 아니다.
새 외형/명예 모션/한정 오라 제작도 별도 자산 작업이다.

## 4. 스킬/케어/소각

| 등급 | 스킬 수 |
|---|---:|
| 일반/희귀 | 2 |
| 영웅/전설 | 3 |
| 신수 | 4 |

Reroll(owner,requestId,assetId,revision,slotIndex)만 받는다. 서버 종 카탈로그에서
현재 스킬과 다른 스킬을 골라 지정 슬롯을 교체한다. 음수/범위 초과 인덱스,
다른 소유자, 상장/잠금, 오래된 revision, 교체 후보 부족은 거절한다.

비용은 '펫 전체 누적 리롤 수'를 기준으로 계산한다. 슬롯을 바꿔도 초기화되지 않는다.
예시 기본 설정은 min(10억, 1,000 + 250 × 누적수)전. 이 수식/상한은 사용자 미정 값의
검토용 기본값이며 운영 밸런스 확정은 아니다. slotRerollCounts는 슬롯별 기록,
rerollAttempts는 펫 전체 비용 기준이다. 판매해도 초기화하지 않는다.
비용 차감/결과/횟수 증가/소각/영수증 저장은 원자적이다.

Care는 서버 가격으로 Feed/Wash를 수행한다. 포만감/청결 +30, 애정 +5, 최대 100.
기본 가격 Feed 500전/Wash 300전은 검토용 예시다. 이미 가득 찬 대상은 소비하지 않는다.
기존 V1 사료 아이템 케어와 V2 전 직접 소비 케어는 다른 API다. 실제 UI에는 V2를 연결할지,
사료 구매 후 소비할지 한 가지 경제 흐름을 확정해야 한다. 현재 자동 결합하지 않았다.

## 5. 경매

List / BuyListing / Cancel은 펫·알·재료 공통 자산을 사용한다. 거래는 전으로만 한다.
재료는 수량이 들어 있는 묶음 전체를 거래하며 묶음 분할 판매 기능은 아직 없다.
1레벨/아기/각성 성체 모두 펫 거래 규칙이 맞으면 상장할 수 있다.
부화 중인 알, 잠긴 자산, 이미 상장된 자산, 영구 귀속 펫은 거절한다.

수수료는 500~1000 basis point(5~10%) 설정. 기본 예시 5%, 판매자 수령액에서 공제해 소각.
소액 분할 회피를 막기 위해 올림: ceil(price*bps/10000). 예: 101전→수수료 6전.
구매자 차감액=101전, 판매자 수령액=95전. 보석/실타래는 거래에서 움직이지 않는다.

펫은 거래마다 CurrentTradeCount(남은 횟수)를 1 감소한다. 0이면 새 주인에게 영구 귀속.
기존 정책의 계정당 일일 거래 10회 및 펫 이전 후 1시간 재판매 쿨다운을 유지했다.
알/재료는 펫 귀속 횟수 대상이 아니지만 계정 일일 제한에는 포함한다.
상장 유효기간 예시 24시간. 만료 시 구매는 막지만 상장 잠금 해제 배치 작업은 미구현이다.

소유권/목록 revision/잔액/수수료/귀속/활성 offer/영수증은 한 번에 commit해야 한다.
잔액 부족/지갑 한도 초과 시 거래 횟수와 일일 제한까지 rollback한다.
V1과 V2 거래가 같은 AccountState를 사용하므로 일일 제한 및 전 잔액을 공유한다.
수수료와 리롤 소각만으로 인플레이션이 해결됐다고 보지 않는다. 실제 공급/회수 지표와
거래량 시뮬레이션은 아직 하지 않았다.

## 6. 파일과 서버 호출 구조

| 파일 | 역할 |
|---|---|
| Assets/Scripts/EconomyV2/EconomyData.cs | 중복 제거된 공용 모델, 정확한 알 확률, 공개 펫 DTO |
| ServerSources/EconomyContracts.cs | 운영 설정, RNG, transaction 계약, 결제/레이드 검증 인터페이스 |
| ServerSources/EconomyService.cs | 상점/실타래/알/각성/케어/리롤/경매 원자적 도메인 명령 |
| ServerSources/WorldContracts.cs | 기존 전 지갑과 연결, 공통 transaction 계약 |
| ServerSources/Testing/InMemoryWorldStore.cs | 단일 프로세스 로컬 Mock. 운영 배포 금지 |
| Tools/EconomyV2Probe.cs | 실제 서비스 메서드를 실행하는 회귀 검사 |
| Tools/verify_economy_v2.py | Mono 컴파일/실행 및 결과 기록 |

ServerSources는 Unity Assets 바깥에 둔다. 기존 Editor Mock을 생성하는 도구가 필요한
서버 소스를 Assets/Editor/LocalMockGenerated에 UNITY_EDITOR 가드로 복사한다.
이 파일들을 런타임 Assets/Scripts로 옮기지 않는다. 비 Editor 빌드 경계 검사도 실행했다.
실제 운영 클라이언트는 서버 지갑을 임의로 쓰거나 무작위 결과를 결정하지 않아야 한다.

## 7. 미정 설정 목록

운영 확정이 필요한 값은 다음과 같다. 테스트 픽스처에 들어 있는 값은 운영 값이 아니다.

- 일반 알 일반/희귀 확률과 히든 후보 5종의 종 ID/명칭/스킬 풀.
- 등급별 126종 실제 카탈로그와 스킬 데이터. 이번에는 만들어내지 않았다.
- B~E 종별 전 서버 총 발급량.
- 성체 성장 레벨/시간 조건 및 V2 경험치 서비스 연결.
- 레이드 보석 드롭의 확정 확률과 보상 검증 어댑터.
- 시즌 코스튬 가중치/중복 실타래/이월 의상 가격/시즌 전환 시각.
- 리롤 누적 비용식/상한, 먹이/씻기 가격.
- 경매 수수료 5~10% 중 운영 값 및 기존 거래 제한 예시값의 최종 승인.
- V1 6등급→V2 5등급의 데이터 변환 및 비주얼 프로필 대응표.

## 8. 검증 증거

Mono로 현재 공용 모델/실제 서버 서비스/Mock 저장소를 컴파일해 55개 검사를 통과했다.
영롱한 알은 1,000만 구간을 전부 순회해 Common=0, Rare=7,000,000,
Epic=2,500,000, Legendary=499,950, Divine=50임을 확인했다.
히든 확률은 수십억 번 몬테카를로 실험을 한 것이 아니라 RNG에 전달하는 분모 및
성공/실패 경계·전 서버 마지막 한 자리 동시 요청·재시도 방지를 검사했다.

검사 범위: 가격/묶음 수량/반복 요청, 스크롤/부화, 중복 코스튬/실타래/이월 구매,
A~E 각성 및 quota, 성장 조건, 리롤 비용/인덱스/소유권, 케어, 경매 소각/귀속/rollback,
구매번호/레이드 완료 ID 중복 차단, 일반 알 후보, 공개 DTO의 잠재 히든 필드 제외.
기존 SliceProbe와 Editor Mock/비 Editor 경계 검사도 통과했다.

실행 명령:

```bash
python3 Tools/verify_economy_v2.py /absolute/path/to/mono /absolute/path/to/mcs.exe
```

Validation/EconomyV2/results.json에 실제 컴파일/실행 결과와 소스 해시가 있다.
운영 DB·다중 서버·실제 결제·실제 Unity UI/Play Mode·모바일 출시 검증은 수행하지 않았다.
